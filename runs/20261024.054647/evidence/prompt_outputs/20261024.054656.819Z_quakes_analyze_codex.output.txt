## Planning Instructions

### Delivery Shape

A Python command-line application reads saved USGS GeoJSON or fetches a date range and saves the response. Its report commands compute summary, top events, daily counts, regional counts, and nearby events from the saved file. The flow is: parse command and options, fetch or read the FeatureCollection, filter events, calculate the selected report, and write CSV to stdout. Operational and usage failures write diagnostics to stderr and no stdout.

### Test and Acceptance Strategy

Each report story receives focused tests for its formatting, ordering, filters, and empty-result behavior. Data stories receive focused tests for file validation and fetch behavior; fetch tests replace HTTP with a stub and do not use the network. CLI tests cover malformed options, missing or extra files, and exit codes. `bin/test.sh` runs the complete project pytest suite. The terminal ACCEPT-001 story runs the supplied grader unfiltered as the full conformance gate; all implementation and test-runner stories precede it. SEA_TRIALS records the project-wide proof criteria.

### Sequencing and Dependencies

Implement CLI parsing and event loading before report commands. Event loading and filtering support every report. Fetch is an independent command capability using the standard-library HTTP client. Focused tests accompany their implementation scopes; the complete project test runner precedes the terminal grader story. Stage the grader and its snapshot before running final acceptance.

### Source Conflicts and Gaps

No unresolved source conflicts or blockers. The source does not define command help text; planning should supply it as a scoped acceptance criterion.
