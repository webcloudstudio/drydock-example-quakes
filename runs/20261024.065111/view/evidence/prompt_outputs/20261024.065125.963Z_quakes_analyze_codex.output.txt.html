## Planning Instructions

### Delivery Shape

A Python command-line application named `quakes` reads saved GeoJSON FeatureCollections to produce five CSV reports, and fetches feed data from the USGS event service. The primary flow is fetch a date range to a file, then run one or more reports against that saved file. Reports also accept files supplied independently. The supplied harness and snapshot provide offline final verification.

### Test and Acceptance Strategy

Each report story gets focused tests for its command behavior, formatting, relevant options, and edge cases. Fetch tests replace the HTTP call with a stub. The suite must also cover malformed arguments, unreadable or invalid files, region and distance rules, and empty matches.

Final acceptance runs the supplied harness unfiltered from the application root. `VERIFY-001` is the terminal verification story and gates on all implementation stories. The harness exit status is the acceptance verdict.

### Sequencing and Dependencies

Implement shared argument handling, FeatureCollection reading, event normalization, filtering, and CSV output as support for the command stories. Fetch is independently testable through its HTTP stub. Report stories depend on shared reading and filtering behavior. The automated suite exercises all command stories; final harness verification follows their completion and uses the staged snapshot.

### Source Conflicts and Gaps

No unresolved source conflicts or human-owned planning decisions. The sources specify the CLI, runtime, standard-library HTTP client, test runner, command behavior, and offline acceptance harness. Deployment is not applicable to this CLI.
